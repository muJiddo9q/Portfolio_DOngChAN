# 프로젝트 사례 정리

이 문서는 포트폴리오에 넣을 실제 프로젝트 경험을 정리하기 위한 공간이다.

## 작성 방식

각 프로젝트는 아래 형식으로 정리한다.

```md
## 프로젝트 이름

### 프로젝트 개요

무엇을 만드는 프로젝트였는지 간단히 설명한다.

### AI를 활용한 부분

AI를 어떤 작업에 사용했는지 적는다.

### 발생한 문제

AI가 만든 코드, 구조, 설계에서 어떤 문제가 있었는지 적는다.

### 판단과 개선

문제를 어떻게 발견했고, 어떤 기준으로 수정했는지 적는다.

### 팀원과의 논의

팀원과 어떤 내용을 논의했고, 어떤 결론을 냈는지 적는다.

### 결과

수정 후 어떤 점이 좋아졌는지 적는다.

### 포트폴리오에 보여줄 역량

이 사례가 어떤 개발 역량을 보여주는지 정리한다.
```

## 사례 1. Boss FSM과 보스 패턴 구조 리팩토링

### 프로젝트 개요

Unity 6과 Photon Fusion 2 기반의 4인 멀티플레이 보스런 프로젝트에서 보스 AI와 보스 패턴 구조를 구현했다.

### AI를 활용한 부분

AI를 활용해 보스 FSM의 초기 구조를 빠르게 만들었다. 보스의 상태, 추격, 패턴, 사망, 페이즈 전환 같은 큰 흐름을 잡는 데 AI를 사용했다.

### 발생한 문제

초기 구조는 `FSM을 사용한다`는 방향은 맞았지만, 책임 분리가 충분하지 않았다.

코드 기록상 `BossContext_Zero`가 엔진 객체, 스탯, 어그로, 네트워크 상태, 애니메이션 값을 함께 들고 있었고, plain C# 클래스에 `[Networked]` 속성이 들어가 있었다. 또한 보스별 상속 훅과 `_Zero` 전용 클래스들이 많아, 다음 보스를 만들 때 구조를 그대로 재사용하기보다 보스별 코드를 계속 늘릴 위험이 있었다.

즉 문제는 FSM의 존재 여부가 아니라, 보스 공통 구조와 보스별 패턴 확장 지점이 명확히 분리되지 않았다는 점이었다.

### 판단과 개선

리팩토링 과정에서 보스 구조를 다음처럼 나눴다.

- `BossEntity`: Unity/Fusion 생명주기와 객체 조립
- `BossFSM`: 상태 전환과 전역 인터럽트 처리
- `BossStateBase`: 상태 공통 계약
- `BossServices`: 상태와 패턴이 공유하는 협력자 묶음
- `BossNetState`: 클라이언트 표시용 네트워크 방송판
- `BossDefinition`: 보스 스탯과 패턴 목록을 담는 ScriptableObject
- `PatternDefinition`: 패턴 데이터와 런타임 패턴 생성 책임

그 결과 새 보스를 만들 때 FSM 전체를 다시 설계하는 것이 아니라, 보스 정의와 패턴을 추가하는 방식으로 확장할 수 있는 큰 틀이 생겼다.

### 팀원과의 논의

AI가 만든 결과물을 그대로 확정하지 않고, 팀원과 아키텍처를 논의하며 책임 분리, 데이터 흐름, 네트워크 권위, 유지보수성을 기준으로 구조를 다시 잡았다.

### 결과

최종적으로 `보스에 패턴만 추가하면 새로운 보스를 양산할 수 있는 구조`에 가까워졌다.

물론 다음에 다시 만들 때는 패턴 선택 조건, 쿨다운, 애니메이션 타이밍 검증, 테스트 구조 같은 보완점이 남아 있다. 하지만 이 경험을 통해 단순히 FSM 개념을 아는 것을 넘어서, 실제 프로젝트에서 재사용 가능한 구조로 다듬는 과정을 경험했다.

### 포트폴리오에 보여줄 역량

- AI 결과물을 비판적으로 검토하는 능력
- 팀원과 기술적 의사결정을 논의하는 능력
- 유지보수성과 구조를 고려하는 설계 역량
- AI를 도구로 활용하되 개발자가 방향을 잡는 태도
- 상태 머신과 데이터 주도 패턴 구조를 실제 프로젝트에 적용한 경험

## 사례 2. 드로잉툴 구조와 통합 가정 점검

### 프로젝트 개요

Unity 기반 물리 퍼즐 프로젝트에서 플레이어가 선을 그어 퍼즐을 해결하는 드로잉툴을 담당했다.

프로젝트는 스테이지 선택, 드로잉툴, 시뮬레이션, 보상/다음 스테이지 흐름이 이어지는 구조였다.

### AI를 활용한 부분

드로잉툴의 입력, UI, 스테이지 로딩, 시뮬레이션 흐름을 만들 때 AI를 활용했다.

초기에는 내가 생각한 흐름을 기준으로 AI에게 구현을 지시했다.

### 발생한 문제

처음에는 스테이지 선택창에서 드로잉툴 전용 Unity 씬으로 넘어갈 것이라고 생각했다. 그래서 드로잉툴을 독립된 씬 중심으로 바라보며 구조를 잡았다.

하지만 실제 프로젝트 구조는 하나의 앱 흐름 안에서 Addressable로 등록된 UI 프리팹을 로드하고, `UIManager.ShowScene<T>()`를 통해 `StageSelectView`와 `DrawingToolSceneUI`를 전환하는 방식이었다.

즉 문제는 드로잉툴의 기능 구현 자체보다, 프로젝트 전체의 화면 전환 방식과 생명주기 구조를 충분히 확인하지 않은 상태에서 내 가정을 기준으로 구현을 시작했다는 점이었다.

팀장이 “왜 이렇게 했냐”고 물었을 때 나는 “드로잉툴 전용 씬으로 넘어올 줄 알았다”고 답했다. 그때 기능 하나만 볼 것이 아니라, 프로젝트 전체 흐름에 붙을 수 있는 구조까지 고려해야 한다는 점을 깨달았다.

### 판단과 개선

이후에는 더 좋은 구조가 무엇인지, 더 확장성 있는 구조가 무엇인지 신경 쓰며 AI에게 코드 지시를 하려고 했다.

다만 이 문제에는 항상 하나의 정답이 있는 것 같지는 않았다. 프로젝트마다 씬 전환 방식, Addressable 사용 방식, UI 관리 방식, 데이터 주입 방식이 다르기 때문이다.

대신 오답은 비교적 명확했다. 기존 앱 흐름을 읽지 않고 독립 씬이라고 가정하는 것, 데이터 주입 경로를 확인하지 않는 것, 생성/해제 생명주기를 무시하는 것, 팀 전체 구조와 반대 방향으로 구현하는 것은 피해야 했다.

그래서 결론은 “정답을 바로 맞히자”가 아니라 “오답을 피하는 질문을 먼저 하자”에 가까웠다.

### 팀원과의 논의

팀장의 피드백을 통해 내가 맡은 기능만 동작하게 만드는 것과, 팀 프로젝트의 전체 구조에 자연스럽게 붙는 기능을 만드는 것은 다르다는 점을 알게 되었다.

이 경험 이후에는 AI에게 구현을 맡기기 전에 화면 전환 방식, 데이터 흐름, 기존 진입점, 생명주기, Addressable 등록 여부를 먼저 확인하게 하는 프롬프트가 필요하다고 판단했다.

### 결과

이 사례는 아직 완성된 정답을 찾은 경험이라기보다, 구조를 설계하기 전에 어떤 질문을 해야 하는지 배운 경험이다.

포트폴리오에서는 “실패를 통해 구조적 가정을 점검하는 태도를 갖게 되었다”는 사례로 사용할 수 있다. 개발 플레이북에는 배경과 회고를 자세히 남기고, 개인 기술 위키에는 “구현 전 통합 가정 점검 프롬프트”만 담백하게 남겨 다음 프로젝트에서 바로 사용할 수 있게 한다.

### 포트폴리오에 보여줄 역량

- 내 가정이 틀렸을 때 구조 문제가 생길 수 있음을 인식한 경험
- 팀 프로젝트에서 기능 단위가 아니라 전체 앱 흐름을 고려하려는 태도
- AI에게 바로 구현을 맡기기보다, 기존 구조 분석과 확인 질문을 먼저 시키는 방식
- 프롬프트를 단순 명령이 아니라 설계 리스크를 줄이는 기술로 활용하려는 관점
