# AI를 활용하는 개발자

## 문제의식

AI는 코드를 빠르게 생성할 수 있지만, 좋은 결과물을 자동으로 보장하지는 않는다. 요구사항을 잘못 이해하거나, 프로젝트 맥락과 맞지 않는 구조를 만들거나, 당장은 동작하지만 유지보수하기 어려운 코드를 만들 수 있다.

그래서 AI를 잘 활용하는 개발자에게 필요한 역량은 단순히 프롬프트를 잘 쓰는 능력만이 아니라고 생각한다. 문제를 이해하고, 구조를 판단하고, 결과물을 검토하고, 필요한 수정을 다시 지시할 수 있는 개발 지식이 함께 필요하다.

## 나의 활용 방식

나는 AI를 단순한 코드 작성 도구가 아니라, 개발 속도를 높여주는 협업 도구로 활용하려고 한다.

AI에게 모든 판단을 맡기기보다는, 내가 먼저 목표와 제약을 정리하고 필요한 구현 방향을 제시한다. 이후 AI가 만든 결과물을 검토하면서 구조, 책임 분리, 확장성, 유지보수성을 기준으로 다시 수정한다.

## 개인 기술 위키

AI를 더 정확하게 활용하기 위해 나만의 개인 기술 위키를 만들고 있다.

이 위키는 특정 코드를 외워두기 위한 노트가 아니라, 프로젝트 중 바로 확인할 수 있는 핵심 규칙과 프롬프트 모음이다. 자세한 배경과 회고는 별도의 개발 플레이북에 정리한다.

- 알고리즘
- 디자인 패턴
- 아키텍처 구조
- 기술 선택 기준
- 자주 발생하는 문제와 해결 방식
- AI에게 일을 지시할 때 필요한 프롬프트 패턴
- 프로젝트 회고와 개선 사례는 개발 플레이북으로 분리

모든 내용을 손으로 완벽히 구현할 수 있는 상태가 아니더라도, 어떤 상황에서 어떤 접근이 필요한지 알고 있다면 AI에게 더 정확한 지시를 내릴 수 있다. 이 점이 AI를 잘 활용하는 개발자의 중요한 역량이라고 생각한다.

## 프로젝트에서의 경험

과거 멀티플레이 보스전 프로젝트에서 AI를 활용해 보스 FSM 구조를 빠르게 만들었지만, 처음 구조는 확장성과 책임 분리 측면에서 부족한 점이 있었다.

이후 팀원과 함께 아키텍처를 논의하며 `BossEntity`, `BossFSM`, `BossStateBase`, `BossServices`, `BossNetState`, `BossDefinition`, `PatternDefinition`의 책임을 나누는 방향으로 구조를 다시 정리했다. 이 경험을 통해 AI가 만든 결과물을 그대로 사용하는 것이 아니라, 개발자가 방향을 판단하고 개선해야 한다는 점을 배웠다.

또 다른 프로젝트에서는 드로잉툴을 만들며 구조적 가정을 충분히 확인하지 않은 경험이 있다. 나는 드로잉툴이 별도 씬으로 열릴 것이라고 생각했지만, 실제 프로젝트는 Addressable로 등록된 UI 프리팹과 `UIManager.ShowScene<T>()`를 통해 하나의 앱 흐름 안에서 화면을 전환하는 구조였다.

이 경험을 통해 AI에게 구현을 맡기기 전에 먼저 기존 구조를 읽게 하고, 내가 암묵적으로 두고 있는 가정과 확인해야 할 질문을 뽑게 해야 한다는 점을 배웠다. 좋은 프롬프트는 단순히 코드를 빨리 만들기 위한 문장이 아니라, 잘못된 구조를 만들 가능성을 줄이는 설계 도구가 될 수 있다.

## 앞으로의 방향

앞으로도 프로젝트 경험을 통해 얻은 알고리즘, 패턴, 아키텍처 판단 기준을 개인 기술 위키로 정리해 나갈 것이다.

AI를 더 잘 활용하기 위해 필요한 지식을 쌓고, 그 지식을 바탕으로 더 명확하게 문제를 정의하고 더 나은 구조를 설계하는 개발자가 되는 것이 목표다.
