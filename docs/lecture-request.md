# 강의 요청서

> ## 실행 설정 (권장)
> 단계마다 다르다. 전부 최상위로 돌릴 필요 없다.
>
> | 단계 | 모델 | 사고 강도 | 이유 |
> |---|---|---|---|
> | 5번 목차 짜기 | **Opus** | 중간 (`think hard`) | 순서 설계가 강의 품질의 절반. 여기만 잘 나오면 나머지는 따라온다 |
> | 7번 챕터 진행 | **Sonnet** 으로 낮춰도 충분 | **끄기** | 설명글 품질은 사고 예산이 아니라 지식·문장력에서 나온다. 8챕터면 차이가 크다 |
> | 8번 내 코드 대응 | **Opus** | 중간 | 코드를 읽고 개념에 매핑하는 단계 |
> | 9-B 되설명 채점 | **Opus** | 중간 | 미묘하게 **틀리게 이해한 것**을 잡는 단계. 학습의 핵심 |
>
> 모델 전환이 귀찮으면 그냥 Opus로 통일해도 된다. Fast 모드(`/fast`)를 켜면 Opus 품질에 출력이 빨라진다.
> 모드: 일반 세션. **구현 세션과 반드시 분리할 것.**


> **사용법**
> 1. `<< >>` 안의 내용만 채운다. 채운 뒤 `<< >>` 기호는 지운다.
> 2. **구현 세션과 분리된 새 세션**에서 붙여넣는다. 섞으면 둘 다 흐려진다.
> 3. 급하면 **[필수]** 항목만 채워도 된다.
>
> 이 요청서의 목표는 "설명을 듣는 것"이 아니라
> **다음에 AI에게 지시할 때 쓸 어휘를 얻는 것**이다.

---

## 1. 배우고 싶은 주제 [필수]

<< 예: 멀티플레이 액션 게임의 아키텍처 >>
<< 예: 게임 UI를 데이터 기반으로 설계하는 법 >>
<< 예: 캐릭터 능력/스킬 시스템 설계 (GAS 같은 것들) >>

---

## 2. 왜 배우는가 — 최종적으로 만들고 싶은 것 [필수]

<< 동기를 알려주면 강의가 실무 쪽으로 붙는다. 교양 강의가 되는 걸 막는다. >>
<< 예: 4인 협동 보스 러시 게임을 혼자 만들고 싶다. 지금은 싱글만 만들어봤다. >>

---

## 3. 내 현재 수준 [필수]

- **익숙한 것**: << 예: Unity 3년, C#, 싱글플레이 액션 게임 제작 경험 >>
- **이름만 아는 것**: << 예: FSM, 옵저버 패턴, ScriptableObject >>
- **완전히 처음인 것**: << 예: 네트워크, ECS, 어빌리티 시스템 — 용어부터 모름 >>

---

## 4. 역할

너는 상용 << 장르 예: 액션 RPG >> 를 여러 번 출시해본 시니어 클라이언트 프로그래머다.
나를 팀에 갓 들어온 주니어라고 생각하고 **사수처럼** 가르쳐라.
교과서 낭독 말고, 실무에서 실제로 뭘 고르고 뭘 후회했는지를 섞어서 말해줘.

---

## 5. 1단계 — 지금 가르치지 마라. 목차부터.

- 챕터 8개 이내
- 각 챕터: 제목 + 한 줄 요약 + **왜 이 순서인지**
- 선수 지식이 필요한 챕터는 표시
- 목차를 보여준 뒤 내 승인을 기다려라. 승인하면 1챕터부터 하나씩 간다.

---

## 6. 2단계 — 설명 순서 규칙 [이 강의의 핵심]

모든 개념은 **반드시 이 순서**로 설명해라:

```
1. 어떤 문제 상황이 있었는지         (구체적으로)
2. 순진하게 풀면 어떻게 망가지는지    (증상 + 짧은 나쁜 코드)
3. 그래서 나온 해결책
4. ★ 그 해결책의 이름 ★              ← 여기서 처음 이름을 말한다
5. 이 해결책이 오히려 손해인 경우      (= 선택 기준)
```

**이름을 먼저 말하지 마라.** 고통을 먼저 겪게 한 다음 이름을 붙여야 기억에 남는다.
5번이 빠지면 "언제 쓰고 언제 안 쓰는지" 판단이 안 생기니 절대 생략하지 마라.

---

## 7. 챕터 형식

- 한 챕터 = 읽는 데 10분 이내
- 코드는 **개념 설명용 20줄 이내 스니펫만**. 완성 코드 금지
- 챕터 끝에: "실무에서 이걸 안 지키면 생기는 사고" 1개
- 챕터 끝에: 이해 확인 질문 3개 (**답은 주지 마라**)
- 한 번에 여러 챕터를 쏟지 마라. 한 챕터 끝나면 멈추고 내 반응을 기다려라.

---

## 8. 내 코드베이스를 교재로 써라 (선택 — 진행 중인 프로젝트가 있을 때)

`<< 경로 예: Assets/Scripts >>` 를 읽어봐.
방금 배운 개념이 **내 코드 어디에 해당하는지** 대응시켜서 설명해줘.
내가 이미 비슷한 걸 어설프게 하고 있으면 짚어주고, 교과서 방식과 뭐가 다른지 비교해줘.

---

## 9. 이해 확인

챕터마다 둘 중 하나를 하겠다. 내가 고를 테니 물어봐줘.

- **A. 퀴즈**: 방금 챕터로 질문 5개를 내라. 내가 답하면 채점하고 틀린 것만 다시 설명해라.
- **B. 되설명**: 내가 배운 걸 내 말로 설명하겠다. 틀린 곳 / 빠진 곳 / **위험하게 이해한 곳**을 짚어라.

B를 더 자주 쓸 거다. 틀리게 이해한 걸 잡아주는 게 제일 중요하다.

---

## 10. 챕터가 끝날 때마다 저장 [가장 중요한 산출물]

`notes/<< 주제 폴더명 >>/<번호>-<챕터명>.md` 로 저장해줘. 내용:

```
## 핵심 요약        5줄
## 용어 목록  ★     이 챕터에서 나온 기술/패턴 이름 + 한 줄 뜻
                   → 내가 나중에 AI에게 지시할 때 쓸 어휘집이다. 빠짐없이
## 선택 기준        언제 쓰고 언제 안 쓰는가
## 실무 사고 사례    안 지키면 생기는 일
## 내 프로젝트 적용   지금 내 코드에 적용한다면 주의할 점
```

`용어 목록`이 이 강의의 진짜 결과물이다. 요약보다 우선순위가 높다.

# 부록 — 채운 예시

**주제**: 멀티플레이 액션 게임의 아키텍처

**왜**: 4인 협동 보스 러시 게임을 혼자 만들고 싶다. 지금까지 싱글만 만들어봤다.

**수준**:
- 익숙: Unity 3년, C#, 싱글 액션 게임 제작 경험
- 이름만 앎: FSM, 옵저버, ScriptableObject
- 처음: 네트워크 전반, 어빌리티 시스템 — 용어부터 모름

**역할**: 상용 액션 RPG를 여러 번 출시한 시니어 클라 프로그래머. 주니어 사수 모드.

**코드베이스**: `Assets/Scripts` 를 교재로 써줘.

**노트 경로**: `notes/멀티플레이/`
