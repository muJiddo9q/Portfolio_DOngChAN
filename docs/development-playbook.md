# 개발 플레이북

이 문서는 포트폴리오에 넣을 내용과 별개로, 내가 실제 개발에서 다시 꺼내 쓸 수 있는 구조와 판단 기준을 자세히 정리하는 공간이다.

목표는 코드를 전부 외우는 것이 아니다. 다음에 비슷한 문제를 만났을 때 어떤 구조가 좋았는지, 어떤 실수를 피해야 하는지, AI에게 어떤 기준으로 지시해야 하는지를 빠르게 떠올리는 것이다.

## 사용 방식

- 프로젝트에서 만족스러웠던 구조를 기록한다.
- 처음 구조에서 어떤 문제가 있었는지 기록한다.
- 리팩토링 후 어떤 책임 분리가 생겼는지 기록한다.
- 다음에 AI에게 줄 수 있는 지시 문장으로 정리한다.
- 다시 만들 때 보완해야 할 빈틈도 같이 남긴다.

### 언제 쓰는가

여러 종류의 보스를 만들고, 보스마다 다른 패턴을 붙여야 할 때 사용한다.

특히 다음 조건이 있을 때 적합하다.

- 보스가 `Idle`, `Chase`, `Pattern`, `PhaseTransition`, `Staggered`, `Dead` 같은 명확한 상태를 가진다.
- 보스별로 패턴 목록만 바꿔서 확장하고 싶다.
- 패턴의 공통 흐름은 같고, 실제 판정이나 연출만 다르다.
- 네트워크 게임에서 서버가 보스 AI와 전투 판정을 권위 있게 처리해야 한다.
- 클라이언트는 보스 상태를 직접 판단하지 않고 서버가 방송한 상태를 보고 애니메이션과 UI만 갱신해야 한다.

### 처음 문제

초기 구조는 AI를 활용해 빠르게 형태를 잡았지만, 그대로 확장하기에는 책임이 섞여 있었다.

코드 기록에서 확인되는 문제는 다음과 같다.

- `BossContext_Zero`가 `NetworkCharacterController`, `NetworkRunner`, `Transform`, 어그로, 스탯, 네트워크 상태, 애니메이션 값을 한곳에 들고 있었다.
- `BossContext_Zero`는 plain C# 클래스인데 `[Networked]` 속성을 가지고 있었다. Photon Fusion의 `[Networked]`는 `NetworkBehaviour`에서 처리되어야 하므로, 네트워크 방송판의 위치가 잘못 잡힌 구조였다.
- `BossContext_Zero` 생성자에서 `stat`을 만들기 전에 `stat.DetectRange`를 사용해 `AggroSystem_Zero`를 생성했다. 이 흐름은 런타임 예외로 이어질 수 있는 초기화 순서 문제다.
- `BossFSM_Zero`가 현재 상태를 int로 바꾸기 위해 `BossStateChangeToInt()` switch를 직접 들고 있었다. 상태가 늘어나면 FSM 내부 switch도 계속 수정해야 했다.
- `BossPatternState_Zero`가 비어 있거나 패턴 목록을 주입받지 않는 시점이 있었다. 즉 패턴을 보스 구조에 끼워 넣는 확장 지점이 아직 명확하지 않았다.
- `BossEntity_Zero`가 추상 클래스이고 `SkeletonKingBoss_Zero` 같은 보스별 서브클래스가 `OnCommonInit`, `OnServerInit`, `HandleDamage`를 override하는 방식이었다. 보스가 늘어날수록 상속 훅이 늘고, 보스별 차이가 코드 상속 구조로 퍼질 위험이 있었다.

정리하면, 처음 구조의 문제는 `FSM을 쓴다`는 아이디어 자체가 아니라 `어떤 책임이 어디에 있어야 하는가`가 아직 정리되지 않은 상태였다는 점이다.

### 최종 구조

리팩토링 후 구조는 다음 형태로 정리되었다.

```text
BossEntity
  - Spawned에서 서버 전용 객체 조립
  - BossDefinition을 읽어 BossStats, BossHealth, BossMotor, BossTargetSensor, BossServices 생성
  - PatternDefinition[]에서 BossPatternBase[] 생성
  - BossFSM 생성 및 첫 상태 진입
  - ApplyDamage 입구와 Despawn 생명주기 담당

BossFSM
  - 현재 상태 보관
  - ChangeState에서 Exit/Enter 호출
  - 현재 상태의 AnimatorStateId를 BossNetState에 기록
  - Tick 첫머리에서 사망/페이즈 전환 같은 전역 인터럽트 처리
  - 그 외에는 currentState.Tick()에 위임

BossStateBase
  - Enter/Tick/Exit 기본 계약
  - AnimatorStateId 제공
  - FilterDamage 기본 정책 제공

BossServices
  - 상태와 패턴이 공유하는 협력자 묶음
  - Motor, Sensor, Stats, Net, Health를 제공

BossDefinition
  - 보스 한 종의 스탯, 페이즈, 패턴 목록을 ScriptableObject로 보관

PatternDefinition
  - 패턴 공통 시간, 데미지, 해금 페이즈, 애니메이터 패턴 ID를 보관
  - CreatePattern(BossServices services)로 자기 런타임 패턴을 생성

BossPatternState
  - 현재 페이즈에서 사용 가능한 패턴 후보를 고름
  - 선택한 패턴의 Begin/Tick/Cancel 수명주기를 관리
  - 패턴이 끝나면 ChaseState로 복귀
```

### 핵심 책임 분리

`BossEntity`는 조립자다. Unity/Fusion 생명주기, 컴포넌트 조회, 네트워크 객체 despawn 같은 엔진 경계 작업은 여기서 처리한다.

`BossFSM`은 상태 전환 관리자다. 보스가 지금 어떤 상태인지, 전역 인터럽트가 발생했는지, 다음 상태로 언제 넘어가는지를 관리한다.

`BossStateBase`와 개별 상태들은 상태별 행동만 가진다. 예를 들어 `Idle`은 멈추고 타겟을 찾으면 추격으로 넘어간다. `Chase`는 타겟을 향해 이동하고 사거리에 들어오면 패턴 상태로 넘어간다. `PhaseTransition`은 일정 시간 동안 무적을 제공한다.

`BossServices`는 상태들이 공유하는 협력자를 넘겨주는 얇은 묶음이다. 다만 아무거나 넣는 공간이 아니라, 둘 이상의 상태가 실제로 공유하는 객체만 들어가야 한다.

`BossNetState`는 서버가 클라이언트에게 보여줄 값만 담는 방송판이다. 클라이언트가 그 값을 보고 애니메이션, UI, VFX를 갱신한다. AI 판단이나 서버 장부를 넣으면 안 된다.

`BossDefinition`과 `PatternDefinition`은 데이터 확장 지점이다. 새 보스를 만들 때 코드 상속보다 ScriptableObject 데이터와 패턴 클래스를 추가하는 쪽으로 확장한다.

### 이 구조가 마음에 들었던 이유

보스를 새로 만들 때 전체 보스 AI를 다시 짜는 것이 아니라, 큰 틀은 유지한 채 패턴만 추가하면 되는 방향으로 정리되었기 때문이다.

핵심은 `보스 구조`와 `보스 패턴`을 분리한 점이다.

- 보스의 공통 흐름은 FSM이 담당한다.
- 보스별 차이는 `BossDefinition`과 `PatternDefinition`으로 넣는다.
- 패턴의 공통 생명주기는 `BossPatternBase`가 담당한다.
- 개별 패턴은 실제 판정이나 특수 동작만 구현한다.

이 구조 덕분에 다음 보스를 만들 때는 “상태 머신을 다시 설계하기”보다 “이 보스가 어떤 패턴을 가지는가”에 집중할 수 있다.

### 다음에 AI에게 지시할 내용

비슷한 보스 구조를 다시 만들 때는 AI에게 다음 기준으로 지시한다.

```text
Unity/Fusion 기반 보스 AI를 FSM 구조로 만들어라.

조건:
- 서버 권위로 보스 AI와 전투 판정을 처리한다.
- 클라이언트는 서버가 방송한 상태를 읽고 애니메이션/UI만 갱신한다.
- BossEntity는 Unity/Fusion 생명주기와 객체 조립만 담당한다.
- BossFSM은 상태 전환과 전역 인터럽트만 담당한다.
- 상태 클래스는 Enter/Tick/Exit와 상태별 행동만 가진다.
- BossNetState는 클라이언트 표시용 값만 담는 방송판으로 둔다.
- BossServices는 둘 이상의 상태가 공유하는 협력자만 담는다.
- 보스 스탯과 패턴 목록은 BossDefinition ScriptableObject로 분리한다.
- 각 PatternDefinition은 CreatePattern으로 자기 런타임 패턴을 생성하게 한다.
- 새 보스는 가급적 상속 훅을 늘리지 말고 Definition과 Pattern 추가로 확장한다.
```

### 다시 만들 때 보완할 점

현재 구조를 그대로 복사하기보다 다음 부분은 다시 점검해야 한다.

- `BossPatternState`의 패턴 선택이 단순 랜덤에 가까우면 쿨다운, 거리, 상황 조건을 추가해야 한다.
- 여러 보스가 같은 결정론 시드를 쓰지 않도록 `BossID`와 세션/tick 기반 RNG 정책을 확인해야 한다.
- `BossServices`가 점점 커지면 실제 공유 객체인지 다시 검토해야 한다.
- 패턴의 공통 흐름이 더 복잡해지면 Template Method만으로 충분한지 확인해야 한다.
- 애니메이션 타이밍과 판정 타이밍이 어긋나지 않도록 SO 시간과 Animator state 길이를 검증하거나 베이킹하는 도구가 필요하다.
- 상태 전환 테스트, 패턴 인터럽트 테스트, 데미지 무시 정책 테스트가 있으면 구조를 더 안전하게 유지할 수 있다.

### 포트폴리오에서 보여줄 수 있는 역량

이 사례는 단순히 FSM을 사용했다는 경험이 아니라, AI로 빠르게 만든 구조를 코드 리뷰와 리팩토링을 통해 재사용 가능한 구조로 개선한 경험이다.

보여줄 수 있는 역량은 다음과 같다.

- AI 결과물을 그대로 사용하지 않고 구조를 검토한 점
- 네트워크 게임에서 서버 권위와 클라이언트 표시 책임을 분리한 점
- 상태 머신, 데이터 주도 설계, 패턴 확장 구조를 연결한 점
- 상속 훅 중심 구조에서 데이터와 패턴 추가 중심 구조로 개선한 점
- 이후 프로젝트에서도 재사용할 수 있는 개발 플레이북 항목으로 정리한 점

## 구현 전 통합 가정 점검 프롬프트

### 언제 쓰는가

새 기능을 만들기 전에, 그 기능이 프로젝트 전체 구조 안에서 어디에 붙는지 확실하지 않을 때 사용한다.

특히 다음 상황에서 필요하다.

- 새 화면, 새 모드, 새 도구, 새 시스템을 만든다.
- 독립 씬으로 만들지, 기존 씬 안의 UI/프리팹으로 만들지 애매하다.
- Addressable, UIManager, ServiceLocator, Bootstrap, SceneLoader 같은 기존 진입 구조가 있다.
- 내가 맡은 기능만 보면 단순하지만, 실제 앱 흐름에서는 다른 팀원의 구조와 연결된다.
- AI에게 바로 구현을 시키면 내 가정을 그대로 코드로 굳힐 위험이 있다.

### 내 답

이 문제의 답은 “처음부터 완벽한 정답 구조를 맞히는 것”이 아니다.

현실적인 답은 구현 전에 내 가정을 드러내고, 통합 지점을 확인하고, 틀렸을 때 바꿀 수 있는 구조로 시작하는 것이다.

정답은 프로젝트마다 달라질 수 있다. 하지만 오답은 비교적 명확하다.

- 화면 전환 방식이 확정되지 않았는데 독립 씬에 강하게 묶는 것
- 데이터 주입 경로를 확인하지 않고 전역 상태나 임시 참조로 처리하는 것
- 기존 UI/Addressable/부트스트랩 구조를 읽지 않고 새 구조를 따로 만드는 것
- “내 기능만 동작하면 된다”는 기준으로 생명주기와 해제 흐름을 무시하는 것
- 팀 전체가 쓰는 진입점과 반대 방향으로 기능을 구현하는 것

그래서 앞으로는 정답을 바로 찾으려 하기보다, 오답을 피하는 질문을 먼저 던져야 한다.

- 진입점은 무엇인가? 버튼, 라우터, UIManager, Addressable, Bootstrap 중 어디인가?
- 데이터는 어디서 들어오는가? 예를 들어 stage id, stage data, user progress, theme asset은 누가 넘기는가?
- 이 기능이 꺼질 때 무엇을 정리해야 하는가? 입력, 시뮬레이션, 임시 오브젝트, 이벤트 구독, 팝업, 캐시를 확인한다.
- 기존 시스템과 직접 참조해도 되는가, 아니면 인터페이스나 주입 지점이 필요한가?
- 나중에 다른 화면, 다른 스테이지, 다른 테마, 다른 플랫폼에서도 같은 구조를 쓸 수 있는가?
- 최소 구현으로 시작하되, 나중에 바꾸기 어렵게 만드는 결합은 무엇인가?

### 다음에 AI에게 지시할 내용

새 기능을 구현하기 전에 AI에게 바로 코드를 쓰게 하지 말고, 먼저 아래 프롬프트를 준다.

```text
이 기능을 구현하기 전에 프로젝트 통합 구조를 먼저 점검해줘.

목표 기능:
- [여기에 만들 기능을 적는다]

먼저 코드를 작성하지 말고 다음을 확인해줘:
1. 이 기능의 진입점이 새 Unity 씬인지, 기존 씬 안의 UI/프리팹인지, Addressable로 로드되는지 확인해줘.
2. 기존 프로젝트에서 화면 전환, UI 로딩, 데이터 주입, 생명주기를 담당하는 클래스를 찾아줘.
3. 내가 암묵적으로 가정하고 있는 부분을 목록으로 뽑아줘.
4. 각 가정이 틀렸을 때 어떤 구조 문제가 생기는지 설명해줘.
5. 최소 구현안과 확장 가능한 구현안을 비교해줘.
6. 지금 당장 팀장이나 담당자에게 확인해야 할 질문을 뽑아줘.
7. 확인 전에는 바꾸기 어려운 결정을 코드로 굳히지 않는 설계를 제안해줘.

출력 형식:
- 확인한 기존 구조
- 위험한 가정
- 확인 질문
- 권장 구조
- 구현 전 보류해야 할 결정
```

### Unity/씬/Addressable 전용 프롬프트

```text
Unity 기능을 만들기 전에 씬 의존성부터 점검해줘.

다음 관점으로 기존 코드를 읽고 설계안을 제시해줘:
- 실제 Unity SceneManager.LoadScene을 쓰는가?
- 아니면 UIManager.ShowScene, Addressable prefab, panel stack 같은 자체 화면 전환을 쓰는가?
- 새 기능은 씬에 직접 배치되는가, 프리팹으로 등록되는가, 런타임에 인스턴스화되는가?
- 이 기능이 필요한 데이터를 누가 전달하는가?
- Awake/Start/OnEnable/OnDisable/OnDestroy 중 어떤 생명주기에 의존하면 위험한가?
- 기능을 닫고 다시 열었을 때 이전 상태가 남을 가능성은 없는가?
- 테스트 가능한 순수 로직과 Unity 오브젝트에 묶인 표현 계층을 어떻게 나눌 수 있는가?

코드를 만들기 전에 먼저 설계 위험과 확인 질문을 제시해줘.
```

### 다시 만들 때 보완할 점

이 프롬프트가 있어도 모든 구조 문제가 사라지지는 않는다.

다음은 여전히 사람이 확인해야 한다.

- 팀장이 생각하는 앱 흐름과 내가 이해한 앱 흐름이 같은가?
- Addressable 등록, 프리팹 배치, 씬 구성은 누가 관리하는가?
- 기능의 책임 범위가 화면 전체인지, 화면 안의 한 패널인지, 순수 로직 모듈인지 명확한가?
- 구현 전에 팀 공통 구조를 최소 한 번은 직접 읽었는가?

프롬프트는 정답을 보장하지 않는다. 다만 내 가정을 보이게 만들고, 오답을 코드로 굳히기 전에 멈추게 해주는 장치다.
