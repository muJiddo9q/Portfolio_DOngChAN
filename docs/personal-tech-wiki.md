# 개인 기술 위키

프로젝트 진행 중 바로 확인하기 위한 핵심 기술 규칙만 적는다.

자세한 배경, 회고, 사례 설명은 `development-playbook.md`에 적는다.

## 공통 원칙

- 구현 전에 기존 구조를 먼저 읽는다.
- 내 가정을 코드로 굳히기 전에 확인한다.
- 기능이 어디서 생성되고, 어디서 꺼지고, 누가 데이터를 넣는지 확인한다.
- 새 구조를 만들기 전에 기존 진입점과 생명주기를 찾는다.
- AI에게 바로 구현을 시키기 전에 위험한 가정과 확인 질문을 뽑게 한다.

## 구현 전 통합 점검

새 기능을 만들기 전에 확인한다.

- 새 Unity 씬인가, 기존 씬 안 UI/프리팹인가?
- Addressable로 로드되는가, 씬에 직접 배치되는가?
- 진입점은 무엇인가? 버튼, 라우터, UIManager, Bootstrap 중 어디인가?
- 데이터는 어디서 들어오는가?
- 기능을 닫을 때 무엇을 정리해야 하는가?
- 기존 시스템과 직접 참조해도 되는가?
- 나중에 다른 화면/스테이지/테마에서도 쓸 수 있는가?

### AI 지시 프롬프트

```text
이 기능을 구현하기 전에 프로젝트 통합 구조를 먼저 점검해줘.

목표 기능:
- [기능 설명]

먼저 코드를 작성하지 말고 확인해줘:
1. 진입점이 새 씬인지, 기존 씬 안 UI/프리팹인지, Addressable인지 확인해줘.
2. 화면 전환, UI 로딩, 데이터 주입, 생명주기를 담당하는 기존 클래스를 찾아줘.
3. 내가 암묵적으로 가정하고 있는 부분을 뽑아줘.
4. 각 가정이 틀렸을 때 생기는 구조 문제를 설명해줘.
5. 팀장이나 담당자에게 확인해야 할 질문을 뽑아줘.
6. 확인 전에는 바꾸기 어려운 결정을 코드로 굳히지 않는 설계를 제안해줘.
```

## Boss FSM 구조

여러 보스에 패턴을 붙여 확장해야 할 때 사용한다.

### 기본 구조

```text
BossEntity
  - Unity/Fusion 생명주기
  - 컴포넌트 조회
  - 객체 조립
  - 데미지 입구

BossFSM
  - 현재 상태 관리
  - 상태 전환
  - 사망/페이즈 전환 같은 전역 인터럽트 처리

BossStateBase
  - Enter/Tick/Exit 계약
  - AnimatorStateId
  - 상태별 데미지 정책

BossServices
  - 둘 이상의 상태가 공유하는 협력자 묶음

BossNetState
  - 클라이언트 표시용 네트워크 방송판
  - 서버 판단 로직을 넣지 않는다

BossDefinition
  - 보스 스탯
  - 페이즈 정보
  - 패턴 목록

PatternDefinition
  - 패턴 데이터
  - 런타임 패턴 생성
```

### AI 지시 프롬프트

```text
Unity/Fusion 기반 보스 AI를 FSM 구조로 만들어줘.

조건:
- 서버 권위로 보스 AI와 전투 판정을 처리한다.
- 클라이언트는 BossNetState를 읽고 애니메이션/UI만 갱신한다.
- BossEntity는 생명주기와 객체 조립만 담당한다.
- BossFSM은 상태 전환과 전역 인터럽트만 담당한다.
- 상태 클래스는 Enter/Tick/Exit와 상태별 행동만 가진다.
- BossServices에는 둘 이상의 상태가 공유하는 객체만 넣는다.
- 보스 스탯과 패턴 목록은 BossDefinition으로 분리한다.
- 각 PatternDefinition은 자기 런타임 패턴을 생성한다.
- 새 보스는 상속 훅보다 Definition과 Pattern 추가로 확장한다.
```

### 주의점

- 패턴 선택은 단순 랜덤으로 끝내지 말고 거리, 쿨다운, 페이즈 조건을 검토한다.
- BossServices가 커지면 실제 공유 객체인지 다시 확인한다.
- 애니메이션 타이밍과 판정 타이밍이 어긋나지 않게 검증한다.
- 상태 전환, 패턴 인터럽트, 데미지 무시 정책은 테스트 대상이다.
