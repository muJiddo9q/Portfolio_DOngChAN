# 설계 상담 요청서

> ## 실행 설정 (권장)
> | 항목 | 권장 | 이유 |
> |---|---|---|
> | 모델 | **Opus (최상위)** | 몇 달을 좌우하는 결정. 여기서 아끼면 나중에 갈아엎는다 |
> | 사고 강도 | **최대** (`ultrathink` 추가 또는 thinking 토글 최대) | 제약 도출 → 옵션 비교 → 단일 추천 → 6개월 뒤 예측. 전부 추론 부하가 큰 작업 |
> | 모드 | **Plan Mode** (Shift+Tab 두 번) | 코드가 물리적으로 안 나와서 설계에 집중된다 |
>
> 상담은 길어야 3~5턴이다. 아낄 자리가 아니다.


> **사용법**
> 1. `<< >>` 안의 내용만 채운다. 채운 뒤 `<< >>` 기호는 지운다.
> 2. Plan Mode(Shift+Tab 두 번)로 들어간다 — 코드가 안 나와서 설계에 집중된다.
> 3. 이 파일 전체를 통째로 붙여넣는다.
>
> 급하면 **[필수]** 항목만 채워도 굴러간다. 나머지는 AI가 되물어본다.
> **모르는 칸은 비우지 말고 "모름"이라고 쓴다.** 빈칸과 "모름"은 완전히 다르다.

---

## 1. 만들려는 것 [필수]

<< 한두 줄. 기술 용어 없이. >>
<< 예: 4인 협동 게임의 보스 전투를 처음 구현한다 >>

---

## 2. 레퍼런스 [필수 — 여기가 제일 중요]

**닮고 싶은 게임 + 어느 축이 닮았으면 하는지**
<< 게임 이름만 쓰면 AI가 엉뚱한 부분을 가져온다. 반드시 "어느 부분"을 붙일 것. >>
<< 예: 몬스터헌터의 "예비동작 보고 회피하는 전투 리듬"만. 전투 한 판 단위. >>

**아닌 것 (반대 레퍼런스)**
<< "이건 아니다"가 "이건 맞다"보다 정보량이 많다. 꼭 쓸 것. >>
<< 예: 부위파괴/소재수집 구조는 아님. 로스트아크식 패턴 암기 강요도 아님. >>

**레퍼런스가 안 떠오르면 → 1인칭 10초 묘사로 대체**
<< 기술 용어 없이, 화면에서 보이는 것과 내가 누르는 것만. >>
<< 예: 보스가 팔을 3초간 치켜든다 → 바닥에 빨간 원 → 나는 굴러서 피한다
       → 옆의 친구는 못 피하고 날아간다 → HP 50% 아래로 가면 갑옷이 깨지고 빨라진다 >>

---

## 3. 내가 아는 사실 [필수]

기술 제약은 몰라도 된다. 아래는 처음 만드는 사람도 다 아는 것들이다.

| 항목 | 내용 |
|---|---|
| 플랫폼 / 유통 | << 예: PC, Steam >> |
| 동시 플레이 인원 | << 예: 협동 4인 >> |
| 한 세션 길이 | << 예: 보스 한 판 5~10분 >> |
| 개발 인원 / 기간 | << 예: 1인, 주말 위주, 6개월 >> |
| 목표 콘텐츠 분량 | << 예: 보스 3종, 각 패턴 6개 >> |
| 현재 엔진 / 프레임워크 | << 예: Unity 6, Fish-Net. 없으면 "아직 안 정함" >> |
| 기존 코드 / 에셋 | << 예: 플레이어 이동·공격은 이미 있음. 싱글 기준으로 짜둠 >> |
| 상용화 여부 | << 예: 포트폴리오용 / 출시 목표 >> |

---

## 4. 내 숙련도 [필수]

- 익숙한 것: << 예: Unity 3년, C# 편함 >>
- 이름만 아는 것: << 예: FSM, 오브젝트 풀링 >>
- **처음인 것**: << 예: 네트워크 동기화 전반. 용어부터 모른다 >>

---

## 5. 내가 모르는 것 (솔직하게)

<< "나는 X를 모른다"를 쓰면 AI의 설명 깊이와 기본값 선택이 달라진다.
   프롬프트가 약해지는 게 아니라 강해진다. >>
<< 예: 서버 권위가 뭔지, 지연 보상이 필요한지, 보스 AI를 뭘로 짜야 하는지 전부 모름 >>

---

## 6. 요청

1. 이 결정에 영향을 주는 변수를 나열하고, 내가 안 밝힌 게 있으면 **질문으로** 던져줘.
   내가 답을 모를 수 있으니 선택지와 일반적인 기본값을 같이 제시해줘.
2. 이걸 구현하는 데 쓰이는 기술/패턴/프레임워크를 **카테고리별로** 나열해줘.
   나는 용어 자체를 모르니 각각 한 줄 설명 + 언제 쓰는지를 붙여줘.
3. 카테고리마다 후보 2~3개를 표로 비교해줘.
   `| 후보 | 구현 복잡도 | 확장성 | 내 상황 적합도 |`
4. 카테고리마다 **반드시 1개를 추천**해줘.
   - "상황에 따라 다르다", "둘 다 괜찮다" **금지**
   - 추천 이유를 내가 준 제약 중 **어느 것 때문인지 연결**해서 설명
   - 각 결정이 "나중에 바꾸기 쉬움 / 어려움" 중 뭔지 표시
5. 각 추천이 **틀렸다는 걸 나중에 어떤 증상으로 알아챌 수 있는지** 한 줄씩.

---

## 7. 규칙

- **코드를 쓰지 마라.** 개념 설명용 의사코드 5줄 이내만 허용.
- 한 번에 다 쏟지 말고, 먼저 나한테 되물을 것부터 물어봐라.
- 내 상황에 과한 설계는 과하다고 말해줘. 1인 개발이다.

---

## 8. 상담이 끝나면

정해진 결정들을 `ARCHITECTURE.md`로 저장해줘. 항목마다 4줄:

```
[결정]      무엇으로 정했나
[이유]      내 제약 중 무엇 때문인가
[안 고른 것] 대안과 탈락 이유
[실패 신호]  이 선택이 틀렸다는 걸 알아챌 증상
```

그리고 `CLAUDE.md`에 한 줄 추가해줘:
> 이 프로젝트의 코드 작업 전 ARCHITECTURE.md를 먼저 읽고 그 결정을 따를 것.

# 부록 — 채운 예시

> 위 템플릿이 실제로 채워지면 이렇게 생겼다.

**만들려는 것**: 4인 협동 액션 게임의 보스 전투를 처음 구현한다.

**레퍼런스**: 몬스터헌터의 "예비동작 보고 회피하는" 전투 리듬만. 전투 한 판 단위.
**아닌 것**: 부위파괴/소재수집 구조 아님. 로스트아크식 패턴 암기 강요 아님. 소울류처럼 한 대에 죽는 것도 아님.

**아는 사실**: PC/Steam · 협동 4인 · 한 판 5~10분 · 1인 개발, 주말, 6개월 · 보스 3종 · Unity 6 + Fish-Net · 플레이어 이동/공격은 싱글 기준으로 이미 구현됨 · 포트폴리오용

**숙련도**: Unity 3년, C# 편함 / FSM·풀링은 이름만 앎 / **네트워크 동기화는 처음, 용어부터 모름**

**모르는 것**: 서버 권위가 뭔지, 지연 보상이 필요한 규모인지, 보스 AI를 뭘로 짜야 하는지 전부 모름.
